Explain the contract before accepting generated code

Start by confirming the interview's tool policy, then state the behavior you intend to implement. Here, keys contain a trusted authorization realm and resource identifier. A completed result is not cached. A failed load is retired so a later call can retry. A bounded registry admits new keys only while capacity is available, but callers joining an existing key remain allowed. The service owner closes outstanding loads during shutdown.

This is one process and one default asyncio event loop, not a distributed duplicate-suppression guarantee. It is not thread-safe. Admission counts registered flights until retirement, not all application requests or a global backend concurrency limit. Dictionary lookup is normally constant time; memory is bounded by the registered-key limit plus tasks and waiting callers outside that registry.

Worked interview answer: "Why not just put every request behind a lock?" That serializes independent resources and can unnecessarily couple cancellation. Sharing one task per key preserves independent work while making same-key ownership explicit. A lock alone does not specify who may cancel the shared task.

Debug a plausible first draft, then explain the minimal repair

Question: "The candidate's implementation passes two successful requests. Why reject it?" Ask how cancellation propagates. A plausible first draft ends get with return await task. If one waiter awaiting that task is cancelled, it can cancel the shared task and disrupt another waiter. Two successful calls do not test that property.

The local regression replaced only the shielded await with the direct await in an isolated copy. The cancellation test failed with CancelledError at the surviving waiter's await. Restoring asyncio.shield made the test pass. No timing or traffic measurement is inferred from that result. Preserve the failing trace and identify the ownership rule it contradicts rather than rewriting the entire implementation.

Worked answer: "What does shielding fail to solve?" It does not stop an explicit owner cancellation, a loader failure or an event-loop shutdown. It also does not decide whether work should continue after every waiter leaves. Here, work remains registered until completion or owner shutdown. For expensive operations, another design may track waiter counts and cancel orphaned work; that changes the contract and needs additional race tests.

Separate a correct primitive from a safe platform integration

The key must represent the complete sharing boundary. Tenant plus resource can be insufficient when users in the same tenant have different entitlements or request parameters. Authenticate and authorize before constructing the key; include any permission scope or result-shaping input that changes whether sharing is allowed. Deduplication is not an authorization check.

create_task normally copies the first caller's context. A loader that implicitly reads caller credentials or tracing context can therefore inherit the first caller's identity while serving other waiters. Bind backend authority explicitly and decide how operation-level telemetry represents shared work. Do not use an ambient principal as a substitute for the validated sharing boundary. Capacity rejection also needs an application policy: fail fast, retry with bounded backoff or use another queue. Putting an unbounded queue around a bounded registry simply moves the memory problem. Distinguish admitted flights, waiting callers and backend resource limits in the explanation.

What should the interviewer learn from this exercise? Whether the candidate can reason about ownership, maintain a falsifiable explanation and make a small verified repair.
