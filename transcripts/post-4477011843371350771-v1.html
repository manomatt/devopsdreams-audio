Incident Response Playbooks for Kubernetes and EKS: Evidence, Containment, and Recovery

This is the AI-narrated article. The prose follows the written post; pronunciation is adjusted, and code and images are announced separately.

Build Kubernetes and EKS incident playbooks that preserve evidence and contain the actual attack path. Work through pod deletion, compromised workloads, stolen identities, and safe recovery with practical commands.

TL;DR

Effective Kubernetes and EKS incident response connects customer impact, workload state, identity activity, and preserved evidence before responders change production. This guide develops practical playbooks for unexpected pod deletion, compromised containers, stolen service account credentials, and suspected node compromise. It explains scoped evidence collection, Kubernetes audit and CloudTrail correlation, network policy limitations, temporary credential containment, and recovery from trusted artifacts. Use explicit decision gates, separate investigation from destructive actions, and test each containment control in a representative environment. Measure response milestones and recovery quality rather than assuming a successful command proves the incident is resolved.

A playbook should answer the next decision

Deleting a suspicious pod can restore a service while destroying the only remaining evidence of how an attacker entered it. Leaving it running can preserve evidence while allowing continued data theft. Kubernetes and EKS incident response needs an explicit decision about that trade-off, supported by impact, identity, and telemetry.

An incident response playbook is a scenario-specific operating procedure: its trigger, scope, evidence requirements, containment options, decision owner, recovery gates, and escalation path should be clear enough for an on-call engineer to use under pressure. A generic instruction such as “review the deployment and restore the pod” leaves the difficult decisions unanswered.

This guide expands that foundation into four practical scenarios. Examples use Bash, AWS CLI v2, kubectl, and jq on an authorized responder workstation. Substitute your account, region, cluster, namespace, and resource names. Collection examples read state; containment and recovery examples change it and must follow your incident authority and change process. These are reference patterns, not results from an executed production incident.

Start by comparing your environment against the EKS security responsibility guidance: a managed control plane does not make workload configuration, identities, or customer data someone else's responsibility.

Use a severity matrix tied to business impact rather than alert names. An illustrative highest-severity trigger is confirmed unauthorized production data access or widespread critical-service failure. A lower-severity investigation might cover a suspicious event with no established compromise. Your organization must choose actual response targets and escalation timings; none of the examples here are universal SLAs.

Avoid treating “cloud-native application security governance” as a special standardized framework without naming a real standard. The useful idea is concrete: prevention during development, admission and deployment controls, runtime detection, and tested incident procedures should share accountable owners and evidence.

Kubernetes auditing defines metadata, request, and response recording levels. A metadata-only event cannot tell you the complete request body. Sensitive request content requires controlled handling; absence from an audit record does not prove it was never read.

The default CloudTrail event history covers 90 days of regional management events; it does not include data events. Configure the relevant data-event collection before relying on it to investigate object-level access. Make cross-account and cross-region search boundaries explicit.

GuardDuty Runtime Monitoring observes runtime behavior using a security agent and does not support EKS workloads on Fargate. Verify actual coverage instead of assuming that an account-level enablement setting covers every pod.

If the deleting identity is still active and unexplained, restored replicas are a temporary availability improvement rather than proof of security recovery.

A standard Kubernetes NetworkPolicy that allows no traffic does not override other selecting standard NetworkPolicies. Kubernetes combines allowed traffic across these policies. Established-connection behavior is implementation dependent, so a new policy may not sever an existing connection. A pod on a compromised host also requires a stronger boundary. These limits are documented in Kubernetes NetworkPolicy semantics.

Before using this approach in production, enumerate every policy selecting the pod and test quarantine in a representative namespace. Existing broad allow policies can defeat the intended result. Updating their selectors can affect other traffic and requires a reviewed design. A custom incident label does not magically exclude the pod from those policies or from its Service.

The Amazon VPC CNI network policy documentation limits support to eligible EC2 Linux configurations; it does not support Fargate or Windows nodes. Verify enablement, agent health, supported configuration, and enforcement before relying on a manifest. For EKS Fargate, establish a tested alternative using available VPC/security-group and workload controls, with careful awareness of the shared resources those changes affect.

Containment gate: confirm attempted new connections along the exploit path fail, examine existing connection behavior, and monitor for continued suspicious activity. Use known benign probes from authorized test locations and available network telemetry. A successful kubectl apply proves that the API accepted an object, not that packets were blocked.

Playbook 3: stolen Kubernetes or AWS workload identity

Trigger: unexpected Kubernetes API access by a service account, or AWS calls by a workload role that cannot be explained by the application's intended behavior.

Kubernetes RBAC, EKS cluster access, and AWS IAM workload permissions are separate authorization paths. Disabling one does not inherently disable the others. EKS supports both IRSA and EKS Pod Identity for workload AWS access; understand which credential mechanism is actually configured. See EKS workload service accounts.

EKS access entries are a cluster access mechanism; they do not replace workload IAM or Kubernetes service-account investigation.

Deleting a pod, removing an IRSA annotation, changing a trust relationship, or removing a Pod Identity association must not be treated as proof that credentials already copied elsewhere are unusable. AWS documents IAM role-session revocation using a time-based deny policy. Evaluate its role-wide impact and propagation, then test denial; blocking new assumptions and restricting existing sessions solve different parts of the problem.

Rotate affected application secrets after closing the path that exposed them. Otherwise, the attacker can simply obtain the replacement. Investigate downstream databases, queues, object stores, and external APIs to which the stolen identity had access.

Cordoning prevents normal new scheduling onto the node. It does not stop running containers or block their network traffic. A scheduling taint is also distinct from isolation; a NoExecute taint can evict pods and alter evidence, so do not substitute it casually.

For EC2-backed workers, establish a tested infrastructure quarantine process that accounts for instance ENIs, security groups, shared group membership, responder access, control plane reachability, and monitoring. Network changes can break healthy workloads on the same node. Consider autoscaler, node-group replacement, and lifecycle controllers that might terminate the evidence source.

kubectl drain is a workload evacuation tool, not an evidence-preservation tool. It can evict pods and remove volatile state; do not execute it as the first forensic action. Its behavior and flags are documented in the kubectl drain reference.

Decide whether active harm requires immediate termination or whether isolated forensic capture is feasible. In a controlled forensic workflow, specialists can capture volatile state and storage artifacts before replacement. An EBS snapshot preserves block-volume contents, not RAM; a container image is not the running container's writable filesystem. Memory acquisition and filesystem collection can themselves alter the system and require appropriate tooling and custody records.

The EKS incident and forensics guidance describes identifying affected pods and nodes, isolation, credential response, evidence capture, and redeployment. Adapt these steps to your compute model: EC2 node access and preservation assumptions do not transfer directly to Fargate.

Recovery: fix the path, rebuild from trust, then prove correctness

Do not recover by deleting compromised pods while leaving their vulnerable controller template unchanged. The controller can recreate the same exposure. Separate the emergency availability action from the permanent corrective change.

Recover in this order:

Fix the exploit path: application vulnerability, unauthorized identity grant, image compromise, unsafe admission configuration, or exposed secret.

Preserve necessary evidence and record the final scope of affected workloads and data.

Deploy a reviewed configuration and verified artifact from an intact build/release path. If the node is suspect, replace it rather than treating a pod restart as host remediation.

Rotate affected secrets and credentials after closing the exposure path. Review downstream impact and consistency.

Restore traffic gradually and watch service behavior and security telemetry together.

Independently verify that the previously abused action fails and the intended customer journey succeeds.

Why this playbook separates evidence, containment, and recovery

These phases have different correctness criteria. Evidence collection asks whether the relevant observations are preserved and traceable. Containment asks whether the attacker's effective path is blocked. Recovery asks whether the intended service and data are trustworthy and functioning. Combining them into “restart and check green pods” hides gaps.

Automation should encode those boundaries. Use incident IDs, resource UIDs, expected account/cluster checks, bounded selectors, dry-run previews where supported, and a recorded rollback. Permit low-risk evidence collection automatically; put broad permission removal, node termination, shared security-group changes, and destructive cleanup behind the established incident decision owner. Re-check resource identity immediately before mutation to avoid acting on a newly recreated object with the same name.

Store playbooks with application and infrastructure changes. Assign an owner and a tested-on record with cluster version, compute model, CNI configuration, credential mechanism, and evidence destination. A playbook last tested against EC2 Linux networking is not automatically valid for another environment.

Frequently asked questions

Is a deleted Kubernetes pod always a security incident?

No. Rollouts, scaling, eviction, and controller reconciliation can remove pods legitimately. Investigate when customer impact, an unexpected actor, suspicious timing, or unauthorized configuration changes make the deletion abnormal.

Does a deny-all NetworkPolicy guarantee pod isolation?

No. Policies are additive, enforcement depends on the network implementation, and established connections may behave differently. Check all selecting policies, platform support, host networking, and actual traffic before declaring containment.

Does deleting a pod revoke its AWS credentials?

No. Temporary AWS credentials copied outside the pod can remain usable until expiry or effective permission denial. Contain the relevant IAM role and access path, then verify attempted use fails without disrupting unrelated workloads unnecessarily.

What evidence should responders capture first?

Record UTC timestamps, exact resource identities, pod and owner specifications, container image digests, current and previous logs, events, and relevant audit records. Protect the archive because specifications and logs may contain secrets or personal data.

How does EKS Fargate change incident response?

EKS Fargate does not provide the same customer-managed node access as EC2 worker nodes. VPC CNI NetworkPolicy and GuardDuty Runtime Monitoring do not support EKS Fargate, so validate alternative network containment and use available audit, application, identity, and network evidence.
