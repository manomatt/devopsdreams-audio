A keyless workflow can still have a large blast radius

Your deployment job has no saved AWS access key. It exchanges a GitHub identity token for temporary credentials. That is a useful improvement—but the role still trusts every repository in the organisation, and its permissions cover every production bucket.

The credential lifetime improved. The authorisation boundary did not.

OIDC makes the caller's identity available to AWS. You must decide which identities may assume a role, which jobs may request tokens, and which operations that role may perform. This article connects those decisions to an illustrative job-permission sketch and a role-trust condition.

The examples illustrate permission and trust boundaries. They do not execute a deployment or certify a production policy.

Follow the identity through four gates

A GitHub job requests an OIDC token. AWS validates that token and evaluates the role's trust policy. If assumption succeeds, the role's effective permissions govern resource access. A protected deployment environment adds a separate gate before the job proceeds.

Questions worth asking during review

Does OIDC eliminate every credential risk? It avoids storing a long-lived AWS key for this federation path. A compromised authorised job can still use the temporary credentials it receives.

Does a production environment subject prove the branch was approved? No. Check environment branch/tag restrictions and review controls. A job allowed to use that environment can carry its environment subject.
