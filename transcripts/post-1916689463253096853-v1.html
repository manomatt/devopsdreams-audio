TL;DR: Importing an AWS resource establishes a Terraform state binding; safe adoption also requires explicit ownership and configuration review. An existing S3 bucket can have years of consumers, policy decisions and operational history behind it. Importing its name into Terraform is easy. Adopting its configuration without changing that history requires a reviewed import-only plan and an agreed owner for each managed setting.

Writing the configuration you wish the bucket had, importing it, then applying the differences combines ownership transfer with an infrastructure change. Separate those decisions so reviewers can see exactly what Terraform will begin controlling.

This example adopts one existing general-purpose bucket and three configuration facets. It was statically reviewed against primary documentation; no AWS discovery, Terraform plan or import was executed.

Establish ownership before choosing an import address

Confirm the AWS account, bucket name, region and owning team. Search existing Terraform states and repositories, CloudFormation stacks and other controllers before calling the resource unmanaged. A missing declaration in your current repository does not prove there is no existing owner.

Terraform expects one resource address per managed remote object. Importing an object into a second state does not negotiate an ownership transfer: both configurations can subsequently try to control it. A coordinated handover must stop the previous controller's reconciliation and preserve its evidence before the new owner applies. Import ownership warning.

The bucket, versioning configuration, bucket-level public-access block and encryption configuration have distinct Terraform resource types. Importing the bucket does not automatically create declarations or state bindings for every configuration facet, nor does it import stored objects. Import workflow, Pinned bucket resource.

Keep discovery files, plans and state outside public repositories. Configure the team's approved backend and workspace before adoption; these example files otherwise use local state.

The credentials must belong to the bucket-owning account. The existing bucket must already have Enabled versioning, AES256 default encryption and all four bucket-level public-access flags true. MFA delete must be disabled or absent. Directory buckets, MFA-delete changes and KMS migration are excluded. If discovery differs, adapt the configuration to preserve existing settings.

Recover from the common encryption mismatch

A realistic failed adoption uses AES256 in the template while discovery reports a customer-managed KMS key. Terraform can propose changing encryption alongside import. The import may be technically valid while the plan violates the no-change boundary.

Reconcile the encryption declaration with the observed algorithm, key and bucket-key setting, verify the key's owning contract, and produce a fresh plan. Any later encryption migration requires separate impact analysis and approval. The pinned encryption resource documents that deleting its Terraform resource resets default encryption, so removing configuration is not safe cleanup.

This is a diagnosis scenario, not an observed cloud failure. Preserve discovery evidence and the rejected plan in practice. Generated configuration can assist unfamiliar imports, but HashiCorp describes it as a best-guess template requiring review. Configuration generation.

Cleanup means forgetting ownership, not deleting data

Before adoption, cleanup involves only local review artifacts. After adoption, do not run destroy to “undo the tutorial.”

For an approved handover, stop applies, preserve a protected state backup and coordinate removal of both resource declarations and import blocks. Review the exact four addresses with terraform state rm -dry-run before authorized state removal. State removal leaves AWS objects intact, but retained declarations can propose recreation and retained imports can adopt them again. Do not remove state during an active run or disable locking to bypass contention. State removal.

The result should be an explicit configuration owner and a repeatable no-change plan. An import receipt alone is not enough.

Frequently asked questions

Does importing the bucket adopt all its settings? No. Manage required facets explicitly and inventory policies, lifecycle rules and other settings outside this example.

Should the initial plan contain no changes at all? It should contain only intended imports. After adoption, review an ordinary plan for unintended infrastructure changes.

Can prevent_destroy protect a removed declaration? No. The rule must remain in the configuration to enforce its protection.

Can I import an object already owned by another state? Arrange a coordinated ownership transfer first; concurrent ownership can produce conflicting reconciliation.
