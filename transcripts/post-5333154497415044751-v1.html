Applying SRE Error Budgets to Services Running on EKS: SLIs, Burn Rates, and Release Decisions

This is the AI-narrated article. The prose follows the written post; pronunciation is adjusted, and code and images are announced separately.

Build error budgets around user requests, not healthy pods. Implement Prometheus burn-rate alerts, diagnose EKS failure modes, and turn reliability evidence into release decisions.

TL;DR

Error budgets turn a service reliability objective into an explicit allowance for unsuccessful user events. For EKS workloads, measure requests at a defined user boundary, calculate good and total events consistently, and distinguish application failures from load balancer failures and missing telemetry. This guide implements request-based SLIs, rolling budget calculations, and multiwindow burn-rate alerts with Prometheus. It also explains latency budgets, low-traffic edge cases, Kubernetes disruption controls, safe release gates, and operational validation. Use the resulting evidence to prioritize mitigation and reliability work without treating autoscaling as a universal response to errors.

Healthy Kubernetes objects can still deliver an unreliable service

An EKS deployment can have ready replicas while checkout requests fail because a database rejects connections. It can also have restarting pods while users see no failures because other replicas absorb the traffic. These situations require different responses, and a pod-health dashboard cannot distinguish them by itself.

SRE error budgets on EKS measure the reliability users receive and turn that evidence into operational decisions. The implementation has four connected steps: define the service objective, measure eligible user events, detect dangerous consumption, and agree what changes are appropriate when reliability deteriorates.

An error budget is an allowance for bad events, not a pool of CPU or replicas. Infrastructure capacity can protect that allowance, but adding capacity does not repair invalid releases, broken credentials, or dependency failures.

The examples below use a hypothetical checkout API with a 99.9% availability objective over a rolling 30-day window. The traffic volumes and incident calculations are illustrative arithmetic, not measured production results. Start by reviewing the EKS reliability guidance against your actual application dependencies and failure boundaries.

Step 1: Define a contract before defining a dashboard

Write an SLO document that answers five questions: which user action, which environment, which eligible events, which success conditions, and which reporting window? Avoid a definition such as “the cluster is available,” which leaves business behavior unspecified.

The latency objective here is separate from availability. A slow success can satisfy the availability objective and fail latency. A failed request also fails this particular latency definition because it requires success. Document that overlap; do not add the two error counts together and call the sum a unique incident count.

For HTTP APIs, status codes require interpretation. A malformed customer request can be excluded or counted as an expected response, depending on the contract. A 429 generated by an unexpectedly small service quota may represent a service failure. A 200 carrying a failed business transaction may be bad. Consistent classification matters more than a blanket “all 4xx are good” rule.

Choose whether retries represent separate attempts or one user operation. Attempt metrics diagnose servers; operation metrics describe whether the user eventually completed checkout. If you use both, give them separate names and denominators. Never count good user operations above bad server attempts.

If N = 20,000,000 and S = 0.999, the allowance is 20,000 bad events. If 8,000 events are bad, 12,000 remain, or 60% of the allowance. Negative remaining budget communicates an actual SLO miss; hiding it with a display clamp loses useful information.

The familiar 43.2-minute allowance comes from 30 × 24 × 60 × 0.001. That is a time-based 99.9% calculation. It is not interchangeable with a request-based budget when traffic varies. Five minutes of failures during a sale can cost more user events than an hour overnight.

A rolling window also changes continuously: older failures and older successes leave the calculation, while new traffic changes N. Budget remaining is a retrospective ratio, not a fixed bank balance guaranteed to grow monotonically. A calendar-month objective has different boundary behavior and should use calendar-aware reporting.

Step 2: Capture the failures your pods cannot see

Place primary accounting at a boundary that sees the complete eligible journey. Instrumentation inside the handler cannot observe TLS failures, requests rejected upstream, or a load balancer with no usable targets. Use edge telemetry and external probes to cover those blind spots, while retaining application counters for diagnosis.

An ALB exposes separate metrics such as HTTPCode_ELB_5XX_Count, HTTPCode_Target_5XX_Count, and RequestCount. Their definitions and dimensions differ; RequestCount only increments when the ALB can choose a target. Adding every 5xx counter and dividing by that metric does not automatically produce a coherent user-facing SLI. Reconcile populations and aggregation periods first. AWS documents ALB metric semantics and statistics.

Step 4: Alert on burn rate, then decide how to respond

Burn rate normalizes the recent bad-event fraction by the permitted fraction:

With a 99.9% objective, 0.1% bad events means burn rate 1; 1% means burn rate 10; 5% means burn rate 50. A threshold of 5% has no special meaning unless it follows from the objective and response policy.

Under a constant request-rate approximation, the fraction of a 30-day allowance consumed over h hours at burn rate b is b × h / 720. Choosing 2% consumption over one hour gives b = 0.02 × 720 / 1 = 14.4. Choosing 5% over six hours gives b = 0.05 × 720 / 6 = 6. Traffic seasonality can make actual event-budget consumption differ, so display event counts alongside these signals.

HPA computes desired replicas from configured resource or custom metrics; it does not come with a universal “error budget allocator.” If error ratio feeds an autoscaler, prove that more replicas improve the causal bottleneck and impose a safe limit. Kubernetes documents HPA behavior and custom metrics.

Retries deserve the same scrutiny. If every pod retries database timeouts several times, doubling pods can multiply database pressure. Bound attempts, use jitter, cap concurrent work, and require idempotency for side-effecting operations. A successful retry can protect a user-operation SLI while increasing backend-attempt failures; both views are useful.

Turn the budget into a release policy with an accountable owner

Burn alerts protect the service during incidents. A budget policy determines what engineering work takes priority afterward. Agree it with product and service owners before a breach, including exceptions for urgent security work and reliability repairs. Google's example error budget policy illustrates using reliability results to govern change.

Avoid embedding this decision in a single unchecked Prometheus query. A release check should record the service, environment, objective, query time, telemetry status, result, and policy version. Secure its read access and separate it from deployment permissions. The person or automation approving an exception should leave an auditable reason.

A canary also needs its own outcome comparison. If only 1% of traffic reaches a broken revision, a global error fraction can look acceptable while that revision fails every operation. Compare revision-specific success with the stable baseline and maintain an overall user SLI. Use bounded revision labels and retire old series to control cardinality.

Why this design separates accounting, diagnosis, and policy

The edge accounting answers “what did users receive?” Application traces and EKS metrics answer “where did the failure happen?” The policy answers “what should the team do next?” Keeping these responsibilities explicit prevents a healthy node count from overruling bad user outcomes and prevents a metric gap from granting release permission.

This also makes ownership clearer. The platform team can own collection and access control while the service team owns success classification and mitigation. Shared dependencies need their own reliability objectives, but their budgets do not erase customer-impacting failures from checkout's budget.

Frequently asked questions

What is an error budget for an EKS service?

An error budget is the allowed fraction or count of bad user events under an SLO during a defined window. For example, 99.9% availability allows 0.1% bad eligible events. Kubernetes health and infrastructure uptime help explain behavior but do not define the user-facing service result.

Should the HPA scale an EKS application when error rate rises?

Scale when a validated capacity signal shows that replicas can reduce the bottleneck. Error fraction alone does not identify capacity shortage; database exhaustion and configuration regressions need different mitigations. Extra replicas can intensify pressure on a saturated shared dependency.

How do I calculate error budget remaining in Prometheus?

Count total and bad eligible events over the same window, calculate the allowance as total multiplied by one minus the objective, and subtract observed bad events. Divide that remainder by the allowance to express a remaining fraction. Treat incomplete history, missing telemetry, and zero-event windows explicitly before making release decisions.

Do PodDisruptionBudgets protect my service SLO?

A PDB constrains supported voluntary evictions for matching pods. It does not guarantee correct requests, prevent node failures, or replace Deployment rollout settings. Combine it with readiness, placement, capacity, dependency resilience, and user-facing measurements.

Should missing SLI metrics count as success?

Missing metrics indicate an unknown measurement state. Alert on absent or partial accounting and use external probes to retain visibility when the serving path or telemetry fails. Automatic release approval should require valid evidence or an explicit accountable exception.

Put one service through the entire workflow

Choose a single user journey, review its eligibility and success contract, and reconcile boundary counts with application observations. Generate the rules, replay representative incidents, confirm notification delivery, and agree an owner-backed release policy. Then extend the same accounting conventions across the fleet while keeping the success criteria specific to each service.
