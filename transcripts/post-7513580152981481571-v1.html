Ready pods can miss a Service selector, an existing cloud object can belong to another Terraform state, and valid AWS credentials do not grant Kubernetes permissions. Each symptom can belong to a different contract, and one successful command cannot establish that the other planes are correct.

Lab one: Ready pods, empty Service endpoints

Question: "All checkout pods are Ready. Why is the Service failing?"

Worked answer: Confirm the intended cluster and namespace, then compare the Service selector with actual pod labels and inspect its EndpointSlices. Readiness does not make a pod match an unrelated selector. A Service can have no matching pods, matching pods that are not ready, or selected endpoints whose port/path is wrong. Establish which case exists before restarting anything. Service debugging

In the illustrative failure, workload labels contain app.kubernetes.io/instance=prod, while the Service selects stage. The mismatch explains absent selected endpoints if no other pods match. A healthy unrelated deployment does not falsify this diagnosis. Also check owner references: an accidental broad selector can route to another workload rather than simply producing no endpoints.

Lab two: Terraform wants to replace an existing object

Question: "The resource still exists in AWS. Why would Terraform replace or recreate it?"

Worked answer: Verify the account, Region, backend, workspace, resource address and exact proposed action. Existence in AWS is not ownership by the selected state. A changed address, wrong workspace or replacement-triggering configuration difference requires different recovery. Read the relevant plan details; do not infer the cause from a summary count.

If an address changed during a refactor, an owner-reviewed moved block can preserve the state association when appropriate. If an object was never managed in this state, import requires deliberate configuration and ownership reconciliation. Neither mechanism should hide an actual immutable-field change. Moved blocks

An approved speculative plan can clarify proposed actions, but it can read remote APIs and acquire the backend lock. Review configuration and permissions before running it against an existing environment. With -detailed-exitcode, zero means no changes, one means an error and two means a proposed difference. Exit two is not a failed Terraform command. A saved plan may contain sensitive values; protect it as an operational artifact. Plan behavior

Refresh-only planning proposes reconciling Terraform's records with remote changes, not repairing infrastructure. Applying that proposal can write state. Avoid using terraform refresh as a diagnostic shortcut: it implicitly approves a refresh-only state update. Do not disable locking to get past an unexplained active writer. Preserve evidence and resolve ownership with the state owner. Refresh semantics

Recovery check: After correcting the address, configuration or state association through its owner, generate a fresh plan and explain every remaining action. Do not apply the earlier replacement proposal merely because an interview prompt says "fix it."

Lab three: AWS credentials work, kubectl is Forbidden

Question: "STS returns an identity. Should I add administrator access?"

Worked answer: First establish whether AWS credentials are valid and which principal kubectl actually uses. GetCallerIdentity describes the AWS caller; it does not grant Kubernetes permissions. The kubeconfig exec plugin can use another profile or assume another role. Inspect its configuration privately, including the selected context and role, without displaying credential material. A Kubernetes Unauthorized response points toward authentication; Forbidden ordinarily means an authenticated request lacked authorization. Read the actual response and requested verb, resource and namespace before diagnosing the path. EKS cluster authentication mode determines whether access entries, the legacy aws-auth mapping or both apply. Access entries and their policies are managed separately from Terraform's AWS execution permissions. EKS access entries

An access entry's Kubernetes groups do not create RBAC permissions by themselves; appropriate RoleBindings/ClusterRoleBindings must exist. EKS access policies can also provide scoped permissions. Evaluate both grant sources: a narrow access policy does not revoke broader RBAC permissions. Verify the policy association and namespace scope with the cluster-access owner, and remember that spelling a nonexistent group or namespace can produce an ineffective grant. AWS IAM policies and EKS access policies are different authorization systems. Access-policy scope

Recovery check: Request the smallest grant for the intended task through the access owner, then verify that the intended operation succeeds and an unrelated privileged operation remains denied. A broad admin grant destroys the evidence about which boundary was missing.
