GA changes the API contract, not the packet path

A DNS gateway answers TCP queries but UDP clients time out. Both route objects exist. The application team sees a networking incident; the platform team sees a successfully reconciled configuration. The missing piece is a transport-specific contract that extends beyond the Route resource.

Gateway API v1.6 moved TCPRoute and UDPRoute into the Standard channel with a v1 API. That makes their configuration surface stable. It does not guarantee that an installed controller supports them, that its Service exposes UDP, or that a firewall admits the return traffic. Treat those as separate acceptance criteria.

This example uses one static DNS backend and two listeners. It makes the protocol boundary visible without relying on public DNS, provisioning a cloud load balancer, or manufacturing benchmark results.

Allocate listeners as scarce infrastructure

TCPRoute and UDPRoute select traffic through an attached listener's protocol and port. They do not offer HTTP host/path matching. A raw TCP listener cannot distinguish tenants by HTTP Host; use the appropriate application-layer route, or TLSRoute where SNI is the routing requirement. TCPRoute's design defines this deliberately narrow model.

Consequently, granting permission to create routes is insufficient as a tenancy policy. Assign a listener to an owner, restrict its allowed route kinds and namespaces, and prevent competing claims through review or admission policy. Multiple routes targeting one raw listener can be Accepted while precedence selects the oldest route, then namespace/name ordering for ties. An Accepted condition alone does not prove that your intended backend receives traffic.

Keep attachment permission and backend permission distinct. Gateway allowedRoutes governs who can attach; ReferenceGrant authorizes cross-namespace backend references. This example keeps both in one namespace. Production platforms should model these permissions separately rather than making every namespace eligible for every listener.

The UDPRoute design leaves shared numeric TCP/UDP listener ports optional and weighted UDP backends at Extended support. Separate ports and one backend avoid those portability assumptions. Standard API availability is a baseline, not a promise about every advanced feature.

Define ownership before production rollout

The platform team owns listener allocation, exposure, controller/CRD compatibility and transport observability. Service owners own backend protocol, readiness and application behavior. Joint acceptance should cover intended-backend selection, UDP-only probes, client-identity consequences and a rollback route to the existing endpoint.

Frequently asked questions

Can TCPRoute route by HTTP Host or path? No. Its raw listener model uses protocol and port; use an application-aware route for HTTP matching.

Can I validate UDPRoute with kubectl port-forward? No. Port-forward supports TCP; send a real UDP query through a UDP-capable path.

Does Accepted guarantee the intended backend receives traffic? No. Check current-generation conditions, competing route precedence, generated exposure and an actual protocol-specific application response.
